# gRPC call-context replay-fixture notes — 2026-05-09

Source class: external research synthesis
Search artifact: `sources/protocol/2026-05-09-0450-grpc-call-context-search-layer.json`

## Scope

This note supports a practical protocol / service-contract workflow page for gRPC-shaped reverse engineering after one protobuf method body is already visible. It is intentionally bounded to proof selection:

- keep protobuf body truth separate from call-context truth
- preserve metadata, deadline/timeout, authority, credentials, cancellation, and final status as first-class replay-fixture material
- prevent replay failures from being misdiagnosed as message-schema failures when the real mismatch is outside the body

It is not a gRPC implementation tutorial, an auth-bypass guide, or a whole-client recreation playbook.

## Source-backed observations

### Metadata is a per-RPC side channel, not payload decoration

gRPC’s metadata guide defines metadata as key/value data associated with an RPC. It is sent as initial or final metadata, implemented using HTTP/2 headers, and commonly carries authentication credentials, tracing information, custom headers, load-balancing/rate-limiting hints, detailed error information, or other application-specific side-channel material. The same guide notes that headers are sent before the initial request data message, trailers are sent when the server closes an RPC, and servers may limit request-header size.

Practical consequence for reverse engineering:

```text
protobuf body recovered != metadata/header contract recovered != same practical RPC call
```

If a replay fixture preserves only serialized protobuf bytes, it may still omit the material that selects auth, routing, tracing, quota, or server-side policy behavior.

### Deadlines and cancellation can change behavior while the body stays identical

gRPC’s deadline guide describes a deadline as the point past which the client is unwilling to wait. By default, gRPC does not set a deadline; clients should set realistic deadlines. If the server exceeds the deadline, the client fails with `DEADLINE_EXCEEDED`; the server side may see cancellation and should stop spawned work. Deadline propagation may convert absolute deadlines into timeouts to avoid clock-skew issues.

The cancellation guide similarly describes cancellation as a signal that the client is no longer interested, with deadline expiration and I/O errors also triggering cancellation. Servers may need to explicitly check and stop long-running work, and cancellation can propagate to upstream calls.

Practical consequence:

```text
body accepted in one run != same lifecycle in another run
```

A body-identical replay can diverge because timeout/deadline posture, cancellation timing, or propagated cancellation changed the call’s lifecycle before the handler reached the same state/effect boundary.

### Status codes are evidence, not automatic root cause

The gRPC status-code reference documents library-generated and application-returned statuses. `DEADLINE_EXCEEDED` can be generated when no response arrives before deadline expiry and may occur even if a state-changing operation eventually completed. `UNAUTHENTICATED` can result from incorrect auth metadata, incompatible credentials, or invalid `:authority` metadata. `UNIMPLEMENTED` may indicate method/cardinality issues, while `RESOURCE_EXHAUSTED`, `UNAVAILABLE`, and parsing/compression errors can be generated by transport/library behavior rather than the application handler alone.

Practical consequence:

```text
status observed != payload schema fault proved != handler consequence disproved
```

A status code is a useful discriminant, but the KB should preserve whether the status came from routing, auth/metadata, deadline/cancellation, cardinality, parsing, server application logic, or transport/library state.

### ClientContext-like APIs expose the practical fixture boundary

The C++ `grpc::ClientContext` reference makes the call-context surface concrete: client code can add metadata, set a deadline, set per-call authority, set call credentials, configure compression, inspect initial/trailing metadata, obtain auth context / peer information, and try to cancel the call. The exact API varies by language, but the source-backed shape is stable: a replay fixture often needs a context object, not only a message object.

Practical consequence:

```text
message object built != ClientContext / call options rebuilt != comparable call issued
```

For reverse work, the cheapest trustworthy constructor may be the generated stub call plus its context/options setup, not a hand-built HTTP/2 replay that loses which context fields mattered.

## Durable KB split

The split to preserve:

```text
service/method route known
  != protobuf body / stream slice recovered
  != metadata/header/trailer contract frozen
  != authority / credential / channel posture matched
  != deadline / timeout / cancellation lifecycle matched
  != final status and trailing metadata interpreted
  != handler-side consumer or durable effect proved
```

Compact memory:

```text
route/body != call-context != lifecycle != status/trailers != consumed/effected
```
