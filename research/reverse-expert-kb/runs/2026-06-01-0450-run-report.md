## New findings
- Microsoft documents `RtlAddFunctionTable` as adding a dynamic function table used on 64-bit Windows to unwind or walk stacks. Dynamic code must provide this table information at runtime; static image metadata alone may be insufficient.
- Microsoft documents `RtlAddGrowableFunctionTable` as range-shaped (`RangeBase`, `RangeEnd`, entry count, maximum count), used for dispatching exceptions through runtime-generated code and for stack backtraces. This makes dynamic unwind ownership a live range / lookup problem, not an API-name problem.
- Microsoft x64 exception-handling documentation describes `RUNTIME_FUNCTION` entries as sorted function-range entries pointing to unwind information, and `UNWIND_INFO` may carry exception / termination handler flags or chained unwind information. Metadata visibility is weaker than handler action or resumed consequence.
- Public guard-page VEH/SEH demo material preserves a useful realism check: `PAGE_GUARD` first delivery is not sustained mechanism truth because the guard is removed after the first violation and must be reapplied when repeated ownership matters.
- Practitioner VMProtect research is useful as case-shape signal that VEH can be a dispatch architecture rather than incidental anti-debug noise; the workflow should ask whether handler delivery carries bytecode / state-machine / trampoline ownership before classifying it as mere friction.
- The sharpened compact splits added this run are:
  - **registered != covering this PC != lookup hit != resumed consequence**
  - **guard configured != first fault != re-armed mechanism != resumed consequence**

## Reflections / synthesis
This run deliberately avoided another native local-service IPC or Linux async continuation after two native-heavy runs. It also avoided browser/mobile, which remain very strong branches. Protected-runtime exception-owned control transfer was already present, but it benefited from external-source pressure because the branch can easily overclaim from recognizable Windows exception artifacts.

The false inferences guarded against are:

```text
RtlAddFunctionTable / RtlAddGrowableFunctionTable observed == this exception PC is owned by that dynamic table
PAGE_GUARD setup or one STATUS_GUARD_PAGE_VIOLATION == sustained control-transfer mechanism proved
VEH hit == incidental anti-debug noise rather than possible dispatch architecture
```

The sharper workflow is:

```text
dynamic unwind case:
  registration/table API
    -> installed base/range/entry material
    -> current exception PC falls inside the owned range
    -> dispatcher/unwind lookup hits the live table or callback-owned range
    -> handler/unwind action or resumed target predicts later behavior

guard/trap case:
  trigger configured
    -> first fault delivered
    -> handler-side branch and context/resume edit observed
    -> guard/trap precondition re-armed when repeated ownership matters
    -> downstream ordinary target or state/effect proved
```

The practical object is still one trustworthy exception-owned transfer boundary, not a broad exception-handling tutorial or a devirtualizer.
