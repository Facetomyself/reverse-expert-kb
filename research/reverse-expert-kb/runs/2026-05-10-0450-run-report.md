## Reflections / synthesis

The protocol / firmware branch already had a strong hardware-observation note for moving from pads, UART/JTAG/SWD/SPI, vendor updates, flash dumps, and bus traces into image-lineage and trigger-linked execution truth. The missing seam was the next narrower boot-chain proof once U-Boot-like evidence is available but still too easy to overread.

U-Boot docs make the split practical rather than stylistic:
- environment variables may be default, saved, or in-memory-only, and `bootcmd` / `bootargs` are only configuration until this boot's current value and use are proved
- Standard Boot separates boot devices, boot methods, and bootflows, with ordering and fallback behavior that can make a found config file weaker than the actual boot attempt
- distro/extlinux files describe candidate labels, kernel/initrd/FDT material, and `append` strings that may use environment substitution, but selected label and final consumed command line still need proof
- `bootm` can rely on current load address, FIT configurations, subimages, initrd, FDT, and overlays; a FIT container is not one flat executed image
- FIT / verified boot separates image hashes, image signatures, signed configurations, required keys, and chain-of-trust policy from later handoff and runtime consumption
- Linux command-line parsing gives a useful next-stage consumption surface, but `/proc/cmdline` is also not proof of all bootloader-side source and fallback reasoning by itself

The new workflow note therefore acts as the firmware branch's boot-chain evidence-unit builder before later protocol/parser/static claims lean on “the current firmware image.”
