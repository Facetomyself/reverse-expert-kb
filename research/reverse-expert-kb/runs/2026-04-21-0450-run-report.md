A second launchctl-state split reinforced this run:

A third trigger-realism split reinforced this run:


Concrete practical reinforcements preserved in the KB:
- current `launchctl(1)` documentation preserves that modern `launchd` work is organized around **domains**, **services**, and **endpoints**, with explicit target forms such as `system`, `user/<uid>`, `login/<asid>`, and `gui/<uid>`
- the same documentation explicitly warns that **GUI domains and user domains share many Mach bootstrap names but still have discrete sets of services**, which is strong support for keeping name visibility separate from same-domain service ownership
- `bootstrap | bootout` documentation preserves that loading/removal of services or domains is its own proof object and that some domains implicitly bootstrap predefined paths during creation
- `enable | disable` plus `print-disabled` preserve current domain-targeted disabled-state truth separately from plist-key defaults, and that state persists across boots
- current `launchd.plist(5)` documentation preserves that plist `Disabled` is only the default load behavior and may be overridden externally through `launchctl`
- current `launchctl(1)` preserves that `print` is a current-state surface for on-disk origin, current state, execution context, and last exit status, but explicitly warns the output is **not API**
- current `launchctl(1)` preserves that `kickstart` runs a service immediately regardless of configured launch conditions, making it a useful narrowing surface but weaker than natural trigger proof
- current `launchctl(1)` also preserves that `blame` shows only the **most proximate reason** the service was launched and is intended for debugging/profiling, making it weaker than full durable consumer proof
- Apple’s archived launchd startup guide still preserves the separation between **parameter-load/bootstrap truth** and **actual later request-driven launch truth** for both system daemons and per-user agents
