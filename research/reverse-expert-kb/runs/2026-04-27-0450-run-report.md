## New findings
Primary durable split reinforced this run:

```text
decoder candidate found
  != decoder callsite / slice selected
  != origin bytes or stack-built bytes reconstructed
  != key / IV / immediate constants paired to this artifact
  != decoded bytes materialized and validated
  != artifact provenance preserved
  != first behavior-bearing consumer proved
```

Source-backed details:
- Mandiant / FLOSS material separates decoder-routine identification, xref / argument extraction, emulator snapshots, before/after memory diffs, and readable-string extraction. That is a good provenance ladder, not just a tool pipeline.
- The Mandiant blog also distinguishes initialization-time decoding from decode-immediately-before-use behavior; dynamic observation may therefore show only exercised strings while static/emulated recovery may recover broader inventory.
- Tim Blazytko's Mirai / Binary Ninja writeup shows the stable-decoder case: repeated encoded arguments flow into one helper, and decompiler API automation can preserve caller, argument, and address context while decoding.
- 0ffset's Capstone / Unicorn stack-string writeup shows the harder stack-built / polymorphic-routine case: first preserve construction and local slice boundaries, then emulate when static algebra varies too much.
- Zscaler's Pikabot writeup reinforces layered per-string crypto provenance: encrypted array, array size, per-string RC4 key, shared AES key/IV, output validation, and false-key rejection are separate proof objects.

## Reflections / synthesis
The existing artifact-consumer note starts after recovered material is visible enough to inspect. That is still the right downstream workflow, but it was doing too much implicit upstream work for string-specific cases.

This run makes the upstream proof object explicit:
- flat plaintext lists are triage, not durable evidence
- provenance-preserving decoded strings are durable evidence
- consumer proof remains a separate next step

The new page should help operators avoid two common failures:
1. treating a FLOSS/script/debugger output list as if it already proves current-use behavior
2. patching plaintext into a database and losing original encrypted-byte / decoder / callsite context needed for later proof or reporting

## Concrete scenario notes or actionable tactics added this run
Added a concrete workflow with these tactics:
- classify each recovered string by origin shape: static encoded bytes, stack-built bytes, runtime heap/global construction, emulator diff, or debugger dump
- freeze decoder identity separately from callsite / slice truth
- reconstruct origin bytes before trusting decoded bytes
- pair key / IV / constants to the specific artifact rather than to the sample globally
- treat printable/expected-size output as decode plausibility, not consumer proof
- preserve a consumer-ready record containing origin locator, decoder owner, key/constants, decoded output, output locator, validation reason, and first-consumer candidate
- hand off to `decrypted-artifact-to-first-consumer` only after one string family has stable provenance
