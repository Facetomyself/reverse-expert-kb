## New findings
Primary durable split reinforced this run:

```text
global registerClass or protocolClasses visibility
  != current session/config carries the class
  != default protocols fell through to the custom class
  != canInit(with:) selected the request
  != canonicalRequest(for:) / cache-equivalence truth
  != startLoading() first consumer truth
  != later visible consequence
```

A WebKit-specific split reinforced this run:

```text
scheme handler registered
  != current WKWebViewConfiguration owns that handler
  != current resource uses a scheme WebKit delegates to custom handlers
  != webView(_:start:) fired for this resource
  != resource still needed / not yet stopped
  != page-visible consequence truth
```

Concrete practical reinforcements preserved in the KB:
- Apple’s `registerClass(_:)` documentation preserves that the URL loading system uses the first registered class whose `canInit(with:)` returns true, that registered classes are consulted in reverse registration order, and that there is no guarantee every registered class will be consulted at all
- Apple’s `canonicalRequest(for:)` documentation preserves that canonicalization is implementation-defined but must be stable for the same input and is used for URL-cache lookup and `URLRequest` equality checks; that keeps request-shape similarity separate from cache/canonicalization truth
- Apple’s `URLSessionConfiguration.protocolClasses` documentation preserves that session-local custom classes are checked only after default protocols and cannot be used with background sessions; that keeps config membership separate from current-request ownership
- Apple’s `setURLSchemeHandler(_:forURLScheme:)` documentation preserves that handlers are for custom schemes, that registering one for a WebKit-handled scheme like `https` is a programmer error, and that duplicate registration for the same scheme is also a programmer error
- Apple’s `urlSchemeHandler(forURLScheme:)` documentation preserves that the current configuration can return the handler object or `nil`; that gives a direct current-webview/configuration truth object
- Apple’s `WKURLSchemeHandler` and `webView(_:start:)` documentation preserves that WebKit creates a `WKURLSchemeTask` and calls `start` when the web view encounters a resource with the custom scheme; that grounds `webView(_:start:)` as the first strong scheme-consumer boundary
- Apple’s `webView(_:stop:)` documentation preserves that WebKit may later stop the load because the resource is no longer needed and that further `WKURLSchemeTask` progress reporting after `stop` raises an exception; that keeps start truth separate from resource-still-needed and page-visible consequence truth

## Concrete scenario notes or actionable tactics added this run
- if a custom `URLProtocol` subclass is visible globally, ask first whether the current request even lives in the right runtime/configuration to see it before narrating ownership
- if `protocolClasses` is present, remember Apple says default protocols are checked first and background sessions do not support custom `URLProtocol` subclasses
- if repeated-looking requests still lie, freeze whether `canonicalRequest(for:)` / cache-equivalence truth is the missing object before overreading raw request similarity
- if a `WKURLSchemeHandler` is registered, verify the current scheme is actually custom and not one WebKit already owns, such as `https`
- if `webView(_:start:)` already fired, keep later `webView(_:stop:)` / no-longer-needed truth separate from durable page-visible delivery
- preserve one narrow chain: registration -> current session/webview -> selection -> first consumer -> still-needed truth if relevant -> visible consequence
