## Reflections / synthesis

The protocol / firmware branch already had a strong hardware-observation note and a U-Boot-shaped bootloader-selection note. The missing seam was the desktop/server and UEFI-variable-shaped equivalent: `Boot####`/`BootOrder`/`BootNext`/ESP path evidence can be visible and still not prove which loader image actually started or which later kernel/root/cmdline path owns the behavior.

The source-backed split is practical:
- the UEFI Boot Manager model separates load-option existence, active eligibility, ordered attempt, device path, and boot manager selection
- TianoCore documentation makes fallback concrete: a boot option may return non-success and the boot manager may proceed to the next option
- `efibootmgr` output provides useful current-state surfaces (`BootCurrent`, `BootNext`, `BootOrder`) but those surfaces still need device-path-to-byte and next-stage handoff correlation
- U-Boot `eficonfig` / `bootefi bootmgr` means this same seam can appear inside embedded cases that otherwise look U-Boot-shaped
- UEFI reverse practice often shifts after handoff proof into protocol/service reconstruction of PE-format firmware modules; that is a separate next object, not proof supplied by `Boot####` alone

The resulting KB delta is not “UEFI has boot entries.” It is a reverse-analysis stop rule: prove selected entry, resolved loader bytes, loader start/fallback, policy result if relevant, and one next-stage consumption surface before writing a durable current-boot or current-runtime claim.

## Concrete scenario notes or actionable tactics added this run

Added a new workflow note with concrete tactics:
- classify `Boot####`, active flag, `BootOrder`, `BootNext`, `BootCurrent`, ESP path, and Secure Boot state without upgrading them to execution truth
- compare `BootNext` / `BootOrder` / `BootCurrent` / boot logs before naming a winning entry
- bind UEFI device paths to current bytes: disk/GPT identity, partition GUID, ESP path, loader hash, and optional data
- separate loader start from successful OS or second-stage handoff, especially for shim, GRUB, systemd-boot, Windows Boot Manager, iPXE, recovery utilities, and UEFI shell cases
- treat Secure Boot / verification as policy evidence rather than runtime proof
- stop only after packaging entry identity, selected-entry evidence, resolved loader bytes, fallback/start status, policy result if relevant, next-stage handoff tuple, and first runtime consumer or an explicit gap
