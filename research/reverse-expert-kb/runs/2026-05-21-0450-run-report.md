## New findings
- Microsoft’s Shell Link material frames `.lnk` files as indirection/resolution objects used to access Shell namespace objects. That supports treating shortcut analysis as a proof ladder, not as immediate execution proof.
- `[MS-SHLLINK]` `LinkFlags` controls which structures are present; parser claims should name whether they came from `StringData`, `LinkInfo`, `ExtraData`, tracker blocks, ID lists, or another structure family.
- `StringData` separates relative path, working directory, command-line arguments, and icon location. For malware work, target path, arguments, and current directory should stay separate proof objects until process creation consumes them.
- `LinkInfo` and `TrackerDataBlock` preserve resolution/provenance material such as volume, mapped-drive, UNC context, MachineID, and DROID values. These fields are useful, but they do not prove current activation or process ancestry.
- The practical LNK stop rule added this run is: **artifact != resolved-command != activated != process-created != effect-owned**.

## Reflections / synthesis
The branch-balance reason for this scope was straightforward: the malware branch has many persistence-family continuations, but LNK / Shell Link abuse was still routed only indirectly through generic Startup-folder / persistence wording. That is a real operator gap because shortcut evidence often appears in malware cases as a parsed target/argument artifact, while the durable proof object is a later activation and process/effect chain.

The false inference guarded against is:

```text
suspicious .lnk target / arguments / icon / tracker metadata == executed malware path
```

The sharper workflow is:

```text
specific .lnk artifact
  -> parsed field provenance
  -> current resolved command under host/user context
  -> live activation owner
  -> process creation / ShellExecute consumer
  -> downstream effect
```

The new page deliberately avoids shortcut-construction guidance. It is defensive proof discipline for cases where an analyst already has a suspicious `.lnk` and needs to decide whether it truly owned the process/effect under analysis.
