## New findings
- Microsoft’s Windows Installer documentation keeps deferred script execution, in-script type bits, security context, and rollback/commit behavior separate. Deferred actions are written into the installation script, ordinary session/property visibility is limited, and `NoImpersonate` is meaningful for in-script deferred/rollback/commit families rather than every suspicious row.
- Doyensec’s 2024 repair-path custom-action research is a strong practical reminder that a low-privilege repair trigger can supply user-shaped property/environment material while an `Impersonate="no"` custom action runs under LocalSystem. The proof object is the natural repair path plus poisoned value plus service-side execution plus observed child/file/effect.
- Mandiant’s CVE-2023-6080 case gives a separate writable-path/race seam: during MSI repair, `msiexec.exe` copied and executed a predictable `.tmp` under user `%TEMP%` from SYSTEM context, making `repair path -> high-integrity file create -> attacker-writable namespace / predictable name -> replacement/race -> high-integrity execute` the relevant proof ladder.
- Trend Micro, Qakbot, and Cybereason MSI analyses show the ordinary malware side of the same seam: `CustomAction`, `Binary`, `_Streams`, CAB extraction, directory/property targeting, JScript/VBScript, `regsvr32`, AutoIt, DLLs, or stagers are useful fragments, but the durable claim needs the natural sequence path and first script/process/DLL consumer.
- The compact split added this run is: **CustomAction authored != repair/install/uninstall path selected != context/token/payload trustworthy != writable-path or script/binary handoff controlled != execution consumer ran != malware effect-owned**.

## Reflections / synthesis
This run intentionally moved away from the recent protocol/firmware streak without falling back into browser/mobile. The MSI custom-action page was not missing the broad ladder; it was missing sharper case pressure around the part operators actually misread during malware and installer-abuse work: the middle transition from authored installer metadata into a live path, token, writable-path/script/binary handoff, and first consumer.

The false inference guarded against is:

```text
CustomAction row or embedded MSI stream visible == MSI-owned malware execution proved
```

A more useful operator claim is narrower:

```text
this install/repair/uninstall path selected this action, with this mode/context/token/payload, through this writable-path or script/binary handoff, and this observed consumer/effect
```

## Next-step research directions
- In MSI-shaped malware cases, record `package | trigger path | action | type bits / WiX Execute | sequence table/order/condition | trigger account | token/context | payload source | CustomActionData/property/env | writable path or Binary/CAB/script handoff | process/script/DLL consumer | effect`.
- For repair-path cases, explicitly test whether the selected path can be started by a lower-privilege user and whether the resulting action runs under service/SYSTEM context.
- Treat `%TEMP%`, `%USERPROFILE%`, installer directory properties, CAB/Binary streams, JScript/VBScript, `regsvr32`, `rundll32`, AutoIt, and extracted PE payloads as handoff evidence, not final MSI-owned execution proof.
- If the first consumer is already proven and the remaining question is payload behavior, hand off to staged malware execution, packed-loader, persistence-family, or comms-send-boundary notes rather than continuing to widen MSI table inventory.
