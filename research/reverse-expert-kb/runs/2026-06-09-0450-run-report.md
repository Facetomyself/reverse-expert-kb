## New findings
- Microsoft’s `Assembly.Load` API keeps the runtime load boundary concrete: an assembly can be loaded from a byte array, but that event is runtime acceptance of bytes, not proof that any target method has been selected or invoked.
- Microsoft’s resource APIs keep resource access separate from resource selection and use. A resource entry, manifest stream, or bitmap-looking blob is only carrier evidence until the code path selects it and consumes bytes from it.
- Unit 42’s .NET obfuscation material reinforces the common malware chain: payload material may live in an overlay/resource/stage, be decrypted via AES or similar transforms, then be dynamically loaded and invoked through reflection. The useful proof ladder is carrier -> decode -> loaded stage -> selected target -> first behavior consumer.
- Unit 42’s bitmap-resource case gives a concrete multi-stage example: a benign-looking 32-bit .NET app stores managed stages in bitmap resources, deobfuscates one into a DLL, invokes a method through late binding/reflection, then uses later resources/stages before final payload behavior.
- The cyber.wtf .NET deobfuscation walkthrough reinforces the practical breakpoint: catch `Assembly.Load(...)`, dump the byte array, then resolve the reflection/delegate invocation that starts meaningful execution. It also shows why delegate/proxy indirection means load proof and call-target proof must remain separate.
- The compact split added this run is: **resource/overlay visible != bytes decoded != assembly loaded != target selected/invoked != managed consumer/effect-owned**.

## Reflections / synthesis
This run intentionally avoided another protocol/firmware or malware-persistence leaf. The deobfuscation branch was already strong around native packed startup, write/protect/execute handoff, MBA expressions, string provenance, and opaque successor recovery, but it under-described a very common managed-runtime variant: `.NET resource/overlay bytes -> Assembly.Load -> reflection/delegate target -> managed behavior`.

The false inference guarded against is:

```text
resource list, bitmap blob, dumped DLL, or Assembly.Load hit == payload behavior proved
```

The sharper operator claim is narrower:

```text
this code path selected this carrier, decoded these bytes, loaded this managed assembly, selected/invoked this target, and reached this first config/comms/persistence/next-stage/effect consumer
```

This is useful because .NET malware often has several believable intermediate stages. Stopping at the first recovered DLL can leave the real behavior-bearing target one reflection/delegate/static-constructor hop later.
