## New findings
- COM-shaped evidence is easy to overread because several layers look behavior-adjacent: CLSID/AppID registry mappings, local-server or in-proc launch metadata, running EXE-server class-table publication, `CoCreateInstance` / `CoGetClassObject`, `IClassFactory::CreateInstance`, `QueryInterface`, proxy/stub delivery, and method entry.
- Microsoft COM documentation supports treating registration, class-object/factory resolution, object creation, requested interface binding, and later method invocation as separate proof objects.
- `CoRegisterClassObject` is particularly useful as a runtime-publication boundary: it proves a running EXE server made a class object available, but not that the current client used it or that any behavior-bearing method ran.
- `CoCreateInstance` / `CoGetClassObject` are activation / class-object / object-creation evidence; they should not be narrated as downstream effect proof without one method entry and first handler-owned consumer.
- DCOM activation documentation makes the CLSID/IID request and returned object-reference boundary explicit, which reinforces the stop rule that activation/object-reference truth is weaker than method-consumer truth.

## Reflections / synthesis
Recent autosync runs were source-backed and rotated across deobfuscation, protocol/Linux Netlink, native/ETW, and iOS concurrency. The anti-stagnation requirement was therefore already satisfied, but another external-research-driven pass was still appropriate because Windows COM is a practical native/server seam that was underrepresented compared with D-Bus, Unix-domain sockets, named pipes, ETW, GUI, and async delivery notes.

The practical mistake this run guards against is:

```text
CLSID / COM activation visible == behavior explained
```

The better proof ladder is:

```text
registration artifact visible
  != selected launch context or running class object proved
  != class factory acquired / selected for this client
  != object instance created and requested interface returned
  != correct interface pointer / proxy / apartment path bound
  != behavior-bearing method entered with relevant parameters
  != first handler-owned state change / resource access / launch / reply / effect proved
```

Compact branch memory added:

```text
registered != activated != factory-selected != object-created != interface-bound != method-entered != consumed/effected
```

This complements the existing malware COM/CLSID hijack note without duplicating it: the malware note stays focused on persistence / hijack / natural consumer proof, while the new native note handles the broader COM activation-to-method-consumer boundary used in services, brokers, desktop helpers, shell/Office-style extensions, and local/remote object workflows.
