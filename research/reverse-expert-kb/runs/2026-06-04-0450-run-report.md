## New findings
- OASIS MQTT 5.0 defines an Application Message as payload data plus QoS, Properties, and Topic Name; a Subscription is a Topic Filter plus maximum QoS associated with a Session, and the Server forwards messages that match Client Subscriptions.
- MQTT Packet Identifiers are per-session lifecycle objects. They must be non-zero and currently unused for QoS>0 `PUBLISH`, `SUBSCRIBE`, and `UNSUBSCRIBE`, and become reusable only after the appropriate acknowledgement stage completes.
- MQTT 5.0 explicitly limits required resend behavior: on reconnect with Clean Start 0 and a present session, Client and Server must resend unacknowledged QoS>0 `PUBLISH` and `PUBREL` packets with original Packet Identifiers; this is the only required resend circumstance.
- Retained messages are state-replay artifacts, not necessarily fresh publisher/device events. A retained `PUBLISH` can replace or remove the retained message for a topic, and new non-shared subscriptions receive retained messages according to Retain Handling.
- MQTT 5 properties and subscription options can carry the missing proof object: Subscription Identifier, Topic Alias, Response Topic, Correlation Data, Content Type, Message Expiry, Session Expiry, No Local, Retain As Published, and Retain Handling can change attribution or replay comparability even when topic/payload bytes look identical.
- Mosquitto publish handling shows a concrete implementation split between parse, ACL/plugin acceptance, duplicate/mid handling, store, subscription queueing, QoS acknowledgement, and later outbound/client delivery.
- The compact split added this run is: **PUBLISH captured != broker accepted != subscription/session matched != queued/delivered != ack lifecycle complete != callback/application state consumed**.

## Reflections / synthesis
This run deliberately stayed in a thinner protocol/firmware seam rather than adding another USB/peripheral, native IPC, protected-runtime, or browser/mobile leaf. MQTT is a common IoT/firmware and service-integration protocol, but its false-proof pattern is different from USB HID or BLE: the analyst often sees semantically tempting topic/payload strings and QoS acknowledgements, then overreads them as device/app state truth.

The false inference guarded against is:

```text
MQTT topic/payload or QoS handshake visible == subscriber/device/application behavior proved
```

The sharper workflow is:

```text
PUBLISH captured
  -> broker accepted / authorized / parsed the right topic and properties
  -> subscription/session match selected a delivery target
  -> retained/session-queued/live-publisher class was resolved
  -> QoS packet-identifier lifecycle progressed honestly
  -> client library delivered a callback or queued message
  -> first application state/effect consumer ran
```

This complements the existing BLE and USB HID notes: BLE protects notification/indication delivery-to-consumer proof, HID protects descriptor/report meaning-to-semantic-consumer proof, and MQTT now protects broker-mediated delivery-state-to-application-consumer proof.
