## New findings
- PID-based peer validation is a weaker proof object than audit-token-backed validation in macOS XPC helper work, because PID reuse / wraparound can race code-signing checks.
- `NSXPCConnection` exposes `auditToken` privately; reverse analysis should record whether the helper actually uses an audit-token path or a PID fallback.
- `SecCodeCopyGuestWithAttributes(..., kSecGuestAttributeAudit, ...)` is the stronger peer-identity path to look for when a helper validates XPC clients.
- `SecCodeCopySigningInformation(..., kSecCSDynamicInformation, ...)` and `kSecCodeInfoStatus` can reveal client code-signing policy posture such as library-validation / hardened-runtime flags, but that is a policy gate on the client image, not the same thing as request ownership or helper-owned effect.
- The sharper practical split added this run is: **proxy-visible != accepted != audit-token-validated != policy-checked != request-owned != method-entered != effect-owned**.

## Reflections / synthesis
This run was branch-balance work, not another dense-branch leaf.
The macOS ServiceManagement / XPC helper page already existed, but the search-backed refinement mattered because helper investigations often overread a proxy or PID clue into a trusted client-owned request. The better operator question is whether the helper selected the same audited client, under the expected code-signing policy, before the behavior-bearing method ran.

The practical false stop guarded against is:

```text
client proxy / listener acceptance / PID clue visible == trusted client-owned request proved
```

The sharper ladder is:

```text
client proxy created
  != listener accepted the connection
  != audit-token-based identity was selected
  != code-signing / library-validation policy passed
  != the accepted client sent this behavior-bearing request
  != exported method entered with validated arguments
  != helper-owned effect happened under that trust decision
```
