## New findings
Primary durable split reinforced this run:

```text
configured unit
  != enabled in the relevant system/user manager
  != actual timer/socket/manual activation route in the run that matters
  != correct service instance / passed-FD / start-state truth
  != later malware-owned process/effect
```

A timer-specific split reinforced this run:

```text
user timer exists
  != boot-owned trigger truth
  != calendar catch-up truth
  != later effect
```

A socket-specific split reinforced this run:

```text
socket unit exists
  != Accept=/Service=/template contract proved
  != relevant connection or listener ownership proved
  != descriptor or instance consumer proved
  != later effect
```

Concrete practical reinforcements preserved in the KB:
- `systemd.socket` documents that `Accept=yes` spawns a service instance for each incoming connection and passes only the connection socket, while `Accept=no` passes the listening sockets to one started service unit for all connections
- `systemd.socket` documents that `Service=` is only allowed for `Accept=no`, and that multiple socket units may target one service with ordering between units unspecified
- `sd_listen_fds(3)` documents that passed descriptors begin at fd 3, that descriptor order is undefined across multiple activating socket units, and that the API is not designed for `StandardInput=socket` services
- `systemd-socket-activate(1)` provides a practical reproducible test path for both per-connection and inherited-descriptor socket-activation shapes
- `systemd.service` documents that `Type=simple` start success happens earlier than many analysts assume, `Type=exec` waits for the main binary to execute, and `Type=notify` waits for readiness notification
- `systemd.timer` documents that `OnStartupSec=` in per-user managers is primarily first-login-owned rather than boot-owned, that `OnBootSec=` / `OnStartupSec=` can elapse immediately once activated if already in the past, that `Persistent=true` only affects `OnCalendar=` timers, and that active target units are not restarted on timer elapse

## Concrete scenario notes or actionable tactics added this run
- freeze **system manager vs user manager** early; do not narrate `~/.config/systemd/user` artifacts as boot persistence by default
- if the timer uses `OnStartupSec=`, ask whether the real proof object is first-login user-manager start rather than system boot
- if the timer uses `Persistent=true`, ask whether the timer is actually `OnCalendar=`-based before narrating catch-up truth
- for socket units, freeze `Accept=yes` vs `Accept=no`, same-name service vs `Service=` override vs template-instance requirement, and whether the service consumes descriptors through `sd_listen_fds()` or inetd-style `StandardInput=socket`
- treat one `LISTEN_FDS` observation as descriptor-shape truth first, not automatic proof that the later effect belongs to the suspicious socket you noticed first
- use `systemd-socket-activate` as a narrow reproduction aid when you need to test the concrete socket-activation contract instead of broad unit folklore
