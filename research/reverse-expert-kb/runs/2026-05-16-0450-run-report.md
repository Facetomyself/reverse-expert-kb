## New findings

Primary durable split reinforced this run:

```text
provider known / registered
  != session started
  != provider enabled for this session with relevant level / keywords / filters
  != event write attempted or accepted
  != event delivered to ETL or real-time consumer callback
  != payload decoded and correlated
  != first consumer-owned effect proved
```

Compact branch memory added:

```text
registered != enabled != written != delivered != decoded != consumed/effected
```

The high-value practical addition is that the native/runtime-evidence overlap now has an ETW-shaped workflow page. It prevents a common overread: treating ETW provider metadata, registration hits, `EventWrite` callsites, ETL contents, or callback delivery as if they already prove a downstream rule, alert, reducer, policy, or behavior-changing consumer used the event.

## Reflections / synthesis

Recent autosync runs were external-source-backed and rotated across protocol/firmware, Linux malware, and iOS concurrency. The native branch has practical service/IPC/async/GUI leaves, but ETW was only mentioned incidentally in a few pages. That left a real Windows-native evidence gap: ETW events are often excellent runtime evidence, but their proof boundary is easy to overstate.

The source-backed split is practical:
- Microsoft’s overview separates session control, provider instrumentation, and event consumption as distinct roles.
- Session configuration material separates `StartTrace` from provider enablement through `EnableTrace*` / `EnableTraceEx2`.
- Provider APIs (`EventRegister`, `TraceLoggingRegisterEx`) establish registration and optional enable-callback surfaces, not delivery or effect.
- Event-write APIs establish provider-side emission attempts, while consuming APIs (`OpenTrace`, `ProcessTrace`, callback setup) establish delivery to ETL or real-time consumers.
- Nothing in those earlier boundaries proves a downstream rule, reducer, alert, score update, UI change, database write, or service action; that remains the first consumer-owned effect proof.

The resulting KB delta is not “ETW exists.” It is a reverse-analysis stop rule: prove registered, enabled, written, delivered, decoded, and consumed/effected boundaries separately before writing a durable telemetry-to-behavior claim.

## Concrete scenario notes or actionable tactics added this run

Added a new workflow note with concrete tactics:
- classify ETW surfaces as provider-only, controller/session, event-write, consumer/callback, ETL/offline, or downstream rule/action
- bind provider GUID/name, event descriptor/id, level, keywords, schema version, process/thread, and activity ID before making meaning claims
- separate session enablement and filters from provider registration
- separate event-write attempts from ETL / callback delivery
- separate delivery from payload decode and correlation
- separate decoded event evidence from a consumer-owned reducer/rule/action/effect
- package the highest proven ETW boundary plus the next missing boundary instead of narrating a complete telemetry-to-effect chain prematurely
