## New findings
- YARA's structure separates string/hex/regex atoms from the required `condition`; a feature hit is weaker than a condition-level detection decision.
- CERT/SEI guidance gives a useful feature-selection gate for YARA-shaped outputs: selected criteria should be **necessary to behavior** and **sufficient to distinguish** the malware family or behavior from adjacent material.
- Strong YARA candidates often come from behavior-linked strings, resources/config layout, or function bytes. Weak candidates often come from compiler metadata, common libraries, packer stubs, copied/public code, or mutable campaign values.
- Sigma's specification makes `logsource`, `detection`, `condition`, `falsepositives`, `level`, `status`, and relationship/history fields separate rule objects. A behavior story is not a deployable Sigma rule if the target environment lacks the telemetry/schema/fields.
- The sharpened compact rule added this run is: **finding != feature-provenance != rule-semantics != syntax-valid != semantically-validated != deployable**.

## Reflections / synthesis
This run deliberately avoided a convenient new browser/mobile/runtime leaf. The malware branch is already rich in persistence and execution-consumer proof notes, but detection-rule handoff is a different consumer boundary: a reverse finding may be true and still become a noisy, underspecified, or undeployable rule.

The false inference guarded against is:

```text
real RE finding + syntactically valid YARA/Sigma draft == deployable detection
```

The sharper workflow is:

```text
RE finding observed
  -> feature source/provenance frozen
  -> rule language encodes the intended semantic claim
  -> syntax/spec validation passed
  -> positive and negative semantic validation passed or marked missing
  -> telemetry / scan-scope / deployment assumptions satisfied
  -> deployable detection content, or explicitly only hunting/test content
```

The key practical addition is that validation is not one thing. Syntax/spec validation only proves parser/schema acceptance. Positive semantic validation proves representative malicious samples/events match for the intended reason. Negative semantic validation proves adjacent benign, library, packer, sibling-family, admin, installer, EDR, or IT-automation material does not unexpectedly match. Those three states must not be collapsed.
