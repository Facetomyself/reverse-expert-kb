## New findings
- Linux HID documentation frames a report descriptor as the fixed byte contract that describes what HID reports can be sent and what individual bits mean; HID reports themselves carry data values without the descriptor metadata.
- HID reports split into Input, Output, and Feature reports, and Report IDs matter: when present, the report ID is transmitted as the first byte. A device with only one supported report may omit the report ID.
- Linux exposes report descriptors through `/sys/bus/hid/devices/.../report_descriptor` and hidraw descriptor ioctls. Tools like `hid-tools` can decode descriptors and record raw reports for trigger validation.
- Linux hidraw documentation makes the key observation-surface split explicit: hidraw returns reports unmodified, while parsed interfaces apply HID parser behavior. On numbered devices, hidraw `read()` returns report number as the first byte; writes and Feature/Input/Output ioctls also need the report-number/leading-zero convention handled carefully.
- hidraw is recommended for custom or non-conformant devices because parsed descriptor-based interfaces can reject or misinterpret traffic that the device actually uses.
- Parser-library evidence such as `hidparser` reinforces that descriptor parser output can expose reports, fields, bit ranges, usages, arrays, variables, and padding; that output is descriptor-interpretation truth, not live report-instance or semantic-consumer truth.
- The compact split added this run is: **descriptor parsed != report selected != field decoded != live report delivered != parsed/quirked meaning != semantic consumer/effect**.

## Reflections / synthesis
This run deliberately stayed within a thinner practical protocol/firmware seam rather than adding another broad context page. The branch already knew that USB transfer submission/completion can lie, but HID-specific cases fail one layer later: the analyst often sees a descriptor, a usage label, a hidraw byte stream, or an evdev event and overreads that as state/effect ownership.

The false inference guarded against is:

```text
HID descriptor parsed or hidraw bytes visible == semantic device/app behavior proved
```

The sharper workflow is:

```text
descriptor bytes visible
  -> report ID / input-output-feature type selected
  -> field layout decoded with usages, array/variable/padding, ranges, units
  -> one live report instance captured under a trigger
  -> hidraw / evdev / parser / kernel quirk or fixup split classified
  -> first app/device semantic consumer proved
  -> behavior or state effect owned
```

This complements the USB URB note rather than replacing it: URB work answers whether transfer completion/cancel/callback ownership is real; HID work answers whether descriptor/report meaning and first semantic consumer are real.
