## Reflections / synthesis

This was a useful native-branch addition because macOS service/helper reversing has a distinctive false certainty pattern. Plists, `SMAppService.status`, Login Items state, `launchctl` output, `MachServices` names, XPC service bundles, and recovered NSXPC protocols all look operational, but they are often only registration, routing, or contract-selection evidence.

The new workflow page should prevent eight overreads:
1. **registration overread** — helper plist or ServiceManagement status does not prove launchd will route this request now
2. **domain overread** — system, user, GUI-session, process-domain, and bundled app-private XPC scopes are different proof objects
3. **endpoint overread** — MachServices publication does not prove a helper process is running or ready
4. **identity overread** — helper launch does not prove expected signed helper / user / session / entitlement posture
5. **trust overread** — PID/name/proxy hints are weaker than audit-token, code requirement, entitlement, or authorization checks when trust matters
6. **proxy overread** — client-side `NSXPCConnection` / `remoteObjectProxy` is not listener acceptance or method entry
7. **protocol overread** — recovered NSXPC interface/protocol shape is not deserialization or handler proof
8. **reply overread** — reply/error/interruption/invalidation is not automatically the durable helper-owned effect

This gives the native branch a clean macOS counterpart to Linux D-Bus / AF_UNIX and Windows named-pipe service-helper seams while keeping the iOS XPC and malware persistence branches separate.

## Concrete scenario notes or actionable tactics added this run

Added a concrete workflow with these tactics:
- choose one label / service identifier / Mach service / client selector rather than mapping every helper first
- freeze domain: system LaunchDaemon, user LaunchAgent, GUI session, process-scoped XPC service, bundled app XPC service, or ServiceManagement registered helper
- treat `Label`, `MachServices`, `Program` / `ProgramArguments`, `BundleProgram`, `SMAppService.status`, Login Items state, and `launchctl print` output as setup/routing evidence until one runtime connection is tied to them
- prove helper path, bundle, code signature, effective user/session, sandbox/entitlement posture, and launch reason before attributing privileged or user-scoped effects
- keep proxy route, listener acceptance, exported interface, exported-object method, reply/error, interruption/invalidation, and later state/effect separate
- capture audit-token / entitlement / code-requirement checks as their own boundary when trust is part of the behavior
- stop only after one helper-owned state write, filesystem/database operation, policy reducer, child launch, privileged operation, reply-owned state change, or downstream effect is tied to the accepted request
