## New findings
- Modbus is an application-layer request/response protocol whose standardized function codes and addressing do not by themselves define the target device’s application meaning.
- The Modbus data model uses conceptual banks — coils, discrete inputs, holding registers, and input registers — but a device may implement only subsets, overlap blocks, or use naming conventions that differ from analyst expectations.
- Wire-level PDU addresses are zero-based, while register-map documentation may use one-based register numbers or Modicon-style references such as `40001`; scanner/tool configuration can silently shift the offset.
- Multi-register values are not self-describing. Signedness, scaling, bit fields, string layout, byte order, and word order need validation against a known physical/local-display/gateway/firmware state anchor.
- Exception responses are useful boundary evidence, but they are not final application semantics. For example, `Illegal Data Address` can indicate an invalid range or gap, and `Illegal Data Value` is about request structure/value validity rather than automatically proving an application-level setpoint rejection.
- In Modbus TCP, a Transaction Identifier helps match request and response, but correlation is weaker than proving unit/function/address semantics and later state consumption.
- The compact split added this run is: **map row != PDU offset != accepted access != decoded value != live validation != device-state consumer/effect**.

## Reflections / synthesis
This run stayed in the protocol/firmware branch, but deliberately chose a different practical seam from the recent MQTT, USB HID, and CAN/UDS work. Modbus is common in industrial/IoT firmware and gateway cases, and its false-proof pattern is distinctive: the analyst often sees a vendor register map plus a successful scan and then treats that as the device state model.

The false inference guarded against is:

```text
register-map row or successful FC03/FC06 scan == device state/behavior proved
```

The sharper workflow is:

```text
ADU/PDU captured
  -> unit/slave and transaction/message instance matched
  -> function code and data model selected
  -> address convention translated into the actual PDU offset
  -> range/block access accepted or rejected with the right exception meaning
  -> datatype / scale / word order / bit-field interpretation validated against a known live value
  -> safe write/readback or trigger-linked observation proves the device-side consumer/effect
```

This complements the existing protocol leaves: MQTT protects broker/session/callback delivery proof, USB HID protects descriptor/report meaning proof, CAN/UDS protects diagnostic session/security/response proof, and Modbus now protects industrial register-map-to-device-state proof.

- In Modbus-shaped cases, record `unit | fc | map_ref | pdu_offset | quantity | response/exception | raw words/bits | decode hypothesis | live anchor | consumer/effect | confidence | next check`.
- Treat Modbus TCP transaction identifiers as correlation aids, not application proof.

- Treat exception responses as boundary evidence first; only promote them to application semantics after firmware/gateway/state-consumer evidence supports that interpretation.
