## Reflections / synthesis

The previous two firmware boot-chain notes handled U-Boot/extlinux/FIT and UEFI Boot Manager evidence. Android A/B / AVB has a different failure mode: slot state looks crisp, but the proof objects are split across bootloader metadata, HAL/userspace APIs, slotted partition bytes, verified-boot policy, rollback storage, and updater success marking.

Official / source-backed material makes the split practical:
- AOSP A/B docs describe redundant partition sets where the running system uses one slot while the inactive slot can be updated; being selected for next boot is not the same as reaching stable userspace.
- Boot Control HAL exposes current slot, active slot selection, successful marking, unbootable marking, bootable queries, successful queries, and suffix lookup as distinct surfaces.
- AVB documentation separates vbmeta signature / descriptor verification, rollback indexes baked into images, and stored rollback indexes in tamper-evident storage.
- U-Boot’s Android A/B support shows how `bcb ab_select` reads `misc` metadata and emits `androidboot.slot_suffix=` / `root=` material, while U-Boot AVB support shows `avb verify [slot_suffix]` as a separate policy gate.

The resulting KB delta is not “Android uses A/B slots.” It is a reverse-analysis stop rule: prove active-for-next, current suffix, resolved image tuple, AVB / rollback acceptance, userspace consumption, success/retire state, and one first behavior owner before writing a durable current-slot claim.
