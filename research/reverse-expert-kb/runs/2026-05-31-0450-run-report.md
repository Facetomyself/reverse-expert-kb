## New findings
- Microsoft documents ALPC ETW events under the NT Kernel Logger with event types for send message, receive message, wait for reply, wait for new message, and stop waiting. These are useful boundary events, but they are not handler-dispatch or effect proof without target-local correlation.
- Public ALPC internals writing emphasizes the connection-port / communication-port split: a visible named port under `\\RPC Control` is often only the connection surface, not proof of an accepted client or a live request handler.
- `PORT_MESSAGE` fields exposed by phnt — length, type, data-info offset, client id, message id, callback id / client-view-size — are good correlation fields, but they do not by themselves prove semantic opcode, attribute/view/handle consumption, security posture, or effect ownership.
- ALPC message attributes, sections/views, handle attributes, security attributes, and port context can carry the behavior-bearing proof object outside the flat message payload.
- ALPC identity-sensitive cases need an explicit identity/impersonation split: client PID/TID visibility or port context is weaker than QoS acceptance, successful impersonation, and an operation performed during impersonation lifetime.
- The compact seam added this run is: **port visible != connection accepted != message received != attributes/context decoded != handler dispatched != reply/impersonation/effect owned**.

## Reflections / synthesis
This run deliberately stayed out of browser/mobile and avoided another Linux async leaf after the previous `io_uring` run. Native Windows service/helper IPC still had an operator gap: named pipes and COM were covered, but ALPC is common underneath local services, RPC-like plumbing, and privileged helper paths.

The false inference guarded against is:

```text
\\RPC Control port or ALPC ETW send/receive or NtAlpcSendWaitReceivePort hit == service handler/effect proved
```

The sharper workflow is:

```text
port role frozen
  -> client connection accepted/rejected
  -> message identity and receive site proved
  -> payload / attribute / view / handle / security context decoded
  -> dispatch branch selected
  -> identity / impersonation / reply relation proved if relevant
  -> first handler-owned state/effect observed
```

This fits the KB's consumer-proof style without turning into broad ALPC internals. The practical object is one trustworthy local IPC request chain, not a complete model of every ALPC object.
