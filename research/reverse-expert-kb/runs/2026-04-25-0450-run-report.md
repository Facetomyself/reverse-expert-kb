## New findings
Primary durable split reinforced this run:

```text
physical interface found
  != electrical/protocol session stable
  != artifact bytes acquired
  != bytes mapped to boot partitions / memory ranges
  != current boot actually used those bytes
  != code path executed under the trigger of interest
  != first behavior-bearing consumer identified
```

Source-backed details:
- Wrongbaud's router teardown shows that in-circuit SPI read failure, off-board flash dump success, `binwalk`-visible U-Boot/kernel/SquashFS structures, and UART discovery are separate proof objects.
- William Durand's SPI flash reconstruction writeup shows why `binwalk` offsets need correlation with UART/kernel-log MTD partition lines, carved partition ranges, device tree material, and loader/header observations before the analyst trusts the execution image map.
- HardBreak's JTAG/SWD extraction notes reinforce that target discovery / halt / memory dump are only useful when the memory map, halt state, and dump range are justified.
- Dominik Zürner's SPI instruction-tracing case adds a valuable practical continuation: when debug access is blocked, external flash/XIP bus reads can be treated as trigger-linked fetch/coverage evidence and diffed against idle captures to prioritize the next static slice.

## Reflections / synthesis
The new note fills a pre-protocol gap in the firmware branch. The KB previously had good language for protocol contracts and hardware-side effects after a working image or observed path exists. It had less explicit guidance for the common first hour of a firmware job:

```text
I found pads, got boot output, dumped something, and `binwalk` found files. What exactly do I know?
```

The answer should be image-lineage discipline, not immediate decompilation sprawl. Flash dump, OTA package, live memory view, bootloader map, kernel MTD map, UART boot log, and bus trace are related but not interchangeable. The workflow now gives operators a route to correlate them before deeper parser/rehosting claims.

## Concrete scenario notes or actionable tactics added this run
Added a concrete workflow with these tactics:
- classify each hardware surface by proof object before trusting it
- stabilize UART/SPI/JTAG electrical/session truth separately from acquired bytes or control
- build an image-lineage map across raw flash, vendor OTA, bootloader map, kernel MTD map, and live runtime view
- use UART boot logs as partition/context evidence even when console authority is gated
- use trigger-vs-idle QSPI/XIP bus coverage as a narrow dynamic localization surface when debug access is blocked
- freeze the first behavior-bearing consumer rather than stopping at pads found, dump obtained, or code fetched
