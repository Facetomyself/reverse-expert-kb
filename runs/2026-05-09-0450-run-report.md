## Reflections / synthesis

The protocol branch already had a good generic method-contract -> minimal replay-fixture page and a Windows-RPC-specific continuation around binding/auth/context lineage. The missing thin seam was the analogous gRPC-specific call-context continuation.

Official gRPC material makes the split practical rather than stylistic:
- metadata is a per-RPC side channel implemented as HTTP/2 headers/trailers
- deadlines and cancellation can change behavior while the body stays identical
- status codes may be library-generated, application-returned, or ambiguous
- `ClientContext`-style APIs expose metadata, deadline, authority, credentials, compression, cancellation, and metadata/status observation as one practical fixture surface

That supports a workflow note whose first proof object is not just `method + protobuf bytes`, but `method + body + call-context + lifecycle + status/trailers`.
