## New findings
- Linux kernel overlay documentation frames overlays as modifications to the kernel live tree whose effects may create or deregister devices. That is stronger than static DTS evidence, but still not proof of successful driver probe or behavior ownership.
- U-Boot overlay documentation places overlay application inside the boot tuple: base DTB + DTBO load, working FDT selection, resize, `fdt apply`, and boot with the modified FDT. Reverse work should keep those as FDT-lineage facts before driver claims.
- Linux platform-device and driver-binding documentation keeps enumeration/resources, match/bind, `probe()`, per-device state, and sysfs links as separate driver-model stages.
- Deferred-probe material gives a concrete embedded false-inference pattern: a plausible node and driver can enter `probe()` but return `-EPROBE_DEFER` because a supplier device such as backlight/regulator/GPIO/clock/reset is not ready. `/sys/kernel/debug/devices_deferred` and supplier-not-ready reasons can be decisive.
- The practical extension added this run is: **base DTB visible != overlay selected/applied != live tree mutated != device populated != match/bind selected != probe succeeded after suppliers ready != resource/property consumed != behavior/effect owned**.

## Reflections / synthesis
The branch-balance reason for this scope was practical: firmware/protocol is established, but Devicetree evidence is a common embedded-Linux overclaim point and had not yet been fully routed through the subtree guide / parent page / top-level branch memory. Browser anti-bot and mobile protected-runtime are still strong; native and malware had received several recent precise leaves. Devicetree-to-driver proof is thinner, concrete, and operator-useful.

The false inference guarded against is:

```text
DTB/DTS node, overlay, compatible string, sysfs link, or probe entry visible == driver-owned behavior proved
```

The sharper workflow is:

```text
base/recovered DTB
  -> boot-selected FDT and overlay set
  -> kernel live tree mutation
  -> populated device on the expected bus
  -> match / bind selected
  -> final successful probe after suppliers are ready
  -> exact resource/property consumer
  -> first behavior-bearing effect or handoff
```

This is not a generic Devicetree tutorial. It is a proof-discipline page for reverse cases where an analyst already has DTB/DTS/live-tree/driver evidence and needs to decide whether it really owns a behavior.
