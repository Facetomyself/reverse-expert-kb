## New findings
- Linux ACPI documentation separates ACPI namespace objects from the bus-visible objects drivers usually bind to. `struct acpi_device` / ACPI namespace visibility is often configuration-companion truth, while the behavior-bearing driver object may be `platform_device`, `i2c_client`, `spi_device`, `pci_dev`, or another bus object.
- `_CRS` is current-resource evidence, not effect evidence. It can explain reserved memory/I/O, IRQ, GPIO, SPI/I2C, DMA, bridge windows, or PCI routing, but a reverse case still has to prove OS assignment, driver resolver use, stored state, and first MMIO/IRQ/DMA/handler consumer.
- ACPI-described devices and bus-native devices with ACPI companions are different proof shapes. PCI/USB-like devices may use ACPI for routing/power/configuration while binding and behavior ownership still belong to the bus-visible device and driver.
- `_DSD`, `_DSM`, and vendor AML methods are return-value/control contracts. The practical proof object is not just method existence: prove the method was called with the right contract, decoded, stored, and consumed by the current driver/request/effect path.
- The Toshiba ACPI reverse-engineering case is useful as a concrete method-trace discipline: quiet baseline, one trigger at a time, method arguments/return, caller separation, and hypothesis testing through Linux `acpi_call` or driver instrumentation.
- The new compact stop rule added this run is: **ACPI table visible != namespace node loaded != device enumerated != bus object bound != resource/method consumed != handler/effect owned**.

## Reflections / synthesis
This run deliberately did not add another browser/mobile leaf or another small wording/index-only repair. The firmware/protocol branch already had strong U-Boot, UEFI, Android A/B, and Devicetree boot-to-driver seams, but ACPI remained an under-routed practical case. Without a dedicated page, ACPI evidence could be forced into Devicetree language or left as generic firmware context.

The main false inference guarded against is:

```text
DSDT/SSDT/AML node, _HID/_CID, _CRS, _DSM, or AML trace == device behavior explained
```

The sharper workflow is:

```text
ACPI table / DSDT / SSDT provenance
  -> loaded namespace node under the current OS boot
  -> ACPI-enumerated device or bus-native device with ACPI companion
  -> bus-visible object and driver bind/probe/start
  -> exact _CRS / _DSD / _DSM / method consumer
  -> first handler, MMIO, IRQ, DMA, request, or user/kernel policy consumer
  -> later effect ownership
```

The useful distinction is not “ACPI versus Devicetree” as a taxonomy point. It is operator proof discipline: ACPI can be enumeration root, companion configuration, bridge/routing evidence, or method/control surface. Each role has a different first truthful consumer.
