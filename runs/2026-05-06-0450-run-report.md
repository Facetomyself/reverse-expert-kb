## New findings

Primary durable split reinforced this run:

```text
reverse-engineering finding observed
  != stable feature selected
  != YARA strings/condition or Sigma logsource/detection semantics encoded
  != representative positive and negative material checked
  != false-positive and environment assumptions recorded
  != hunting / triage / production deployment consumer ready
```

Compact branch memory:

```text
observed != feature-selected != encoded != validated != deployable
```

Source-backed details:
- YARA rules separate string definitions from a mandatory boolean condition; a string or atom hit is only a rule component, not the whole detection decision.
- Sigma rules center `logsource` and `detection` sections, while metadata such as `status`, `falsepositives`, `fields`, `level`, `references`, and `tags` carries consumer-facing meaning.
- Sigma status is itself an evidence claim: `experimental`, `test`, and `stable` imply different maturity and production-readiness assumptions.
- VirusTotal’s Sigma rule object reinforces that reusable detection content includes not only matching logic but also log source, false positives, fields, level, references, status, tags, title, and source.
- Practitioner YARA material reinforces the need to choose malware-owned features rather than incidental strings, packer/compiler/library bytes, or one-sample campaign artifacts.

## Reflections / synthesis

This was useful because the malware branch already had evidence packaging, reporting, and handoff guidance, but detection-rule handoff has a sharper failure mode than ordinary reporting. A finding may be locally true and still be a weak rule feature. A rule may be syntactically valid and still be unvalidated. A hunting hypothesis may be useful and still not be production-safe.

The new workflow note should prevent five overreads:
1. **string overread** — one memorable string, mutex, domain, or error message is treated as family-stable detection
2. **packer/library overread** — selected bytes belong to a packer, compiler/runtime helper, copied library, or installer wrapper rather than malware-owned behavior
3. **behavior-to-telemetry overread** — dynamic behavior is observed but the target telemetry/logsource does not actually expose the required fields
4. **draft-rule overread** — valid YARA/Sigma syntax is mistaken for validated detection content
5. **status overread** — experimental or hunting-only content is polished into production-language without validation and false-positive context

This keeps detection handoff inside the reverse-engineering KB as a proof-boundary problem, not a separate broad detection-engineering encyclopedia.

## Concrete scenario notes or actionable tactics added this run

Added a concrete workflow with these tactics:
- freeze the source of each YARA feature: unpacked payload, decoded config, protocol/request-builder material, family-stable helper, packer/compiler/library material, or sample-local campaign artifact
- keep YARA strings / atoms separate from the boolean condition that represents the actual rule decision
- freeze Sigma logsource, field names, normalization assumptions, event visibility, and instrumentation posture before writing detection logic
- treat Sigma `status` as an evidence claim, not decoration
- require positive coverage, negative coverage, false-positive notes, assumptions, status, and next consumer before calling a rule-shaped handoff deployable
