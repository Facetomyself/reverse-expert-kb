## New findings
- I2C device visibility is software-instantiated, not hardware-enumerated. Devicetree/ACPI/board-info/sysfs evidence or an address ACK is weaker than a bound `i2c_client` plus successful driver `probe(...)` and runtime transaction ownership.
- Linux I2C driver docs explicitly warn that detection/probing can be unreliable and side-effect-prone; detect/probe reads are therefore not the same proof object as runtime register behavior.
- SPI evidence has an additional framing risk: controller, `spi_device`, chip-select, mode, speed, bits-per-word, message/transfer split, dummy bytes, async completion, and controller error handling all shape whether raw MOSI/MISO bytes mean what the analyst thinks they mean.
- `regmap_*` helpers are usually closer to semantic register access than raw I2C/SPI calls, but cache policy, volatile/precious register declarations, read-modify-write outcome, paged windows, endian/format conversion, and cache-only/dirty state still decide whether a helper hit equals a hardware-visible behavior.
- The compact split added this run is: **node/bus visible != device bound != transaction issued != completed/ACKed != register decoded/cache-updated != driver consumer ran != effect-owned**.

## Reflections / synthesis
The protocol/firmware branch already had good boot-chain, Devicetree, ACPI, USB, Modbus, MQTT, Netlink, mailbox/doorbell, descriptor, MMIO, and ISR/deferred-worker continuations. It still lacked a narrow serial-control-bus note for the common embedded case where the analyst can see an I2C/SPI peripheral but has not proved the driver-owned register consumer.

The practical correction is:

```text
Devicetree/ACPI child node, I2C address ACK, or SPI chip-select trace
  != bound Linux device/driver
  != successful probe/resource setup
  != one runtime transaction under the trigger of interest
  != transfer completion / ACK / status success
  != decoded register field or regmap cache/RMW truth
  != IRQ, poll, workqueue, or subsystem reducer ran
  != userspace-visible or downstream behavior belongs to this peripheral path
```

This note also creates clean handoffs. If the missing proof is selected live-tree or AML/resource truth, route back to the DT/ACPI pages. If the proof has moved below serial bus traffic into memory-mapped effects, route to peripheral/MMIO. If the bus transaction is merely carrying a higher-level message family, route into parser/state or replay-precondition work. If the first truthful consequence is interrupt/deferred handling, route to the ISR/deferred-worker page.

## Next-step research directions
- In I2C/SPI-shaped cases, record `bus/controller | node/source | address/chip-select | compatible/modalias | driver | probe result | resources | register helper | reg/page/width/mask | transfer API | message/transfer boundaries | status/return | decoded value | regmap cache/RMW | IRQ/poll/workqueue | subsystem callback/state | userspace-visible effect | false stop ruled out`.
- Treat `i2c_transfer(...)`, `i2c_smbus_*`, `spi_sync(...)`, `spi_async(...)`, and `regmap_*` hits as reduction points, not final behavior proof. The next object is usually completion status, decoded register helper state, or first IRQ/workqueue/subsystem consumer.
- For inconsistent bus traces, check phase mismatch first: bootloader preinit, Linux probe/setup, suspend/resume/shutdown, userspace sysfs/debugfs/ioctl access, or another OS slot may own the observed transaction.
- A future narrower pass could cover regmap cache/paging/read-modify-write false stops specifically if repeated cases show `regmap_update_bits(...)` evidence is being overread as hardware-visible state mutation.
