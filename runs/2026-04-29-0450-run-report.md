## New findings

Primary durable split reinforced this run:

```text
host executable selected
  != unresolved DLL name / dependency request observed
  != current search posture frozen
  != attacker-writable candidate path wins before earlier trusted locations
  != malicious DLL loaded into this host process
  != required exports / DllMain / TLS callbacks / initialization passed
  != proxy-forwarding or host-normal behavior preserved when relevant
  != payload or later stage owns one effect
```

Compact branch memory:

```text
hosted != requested != searchable != won-path != loaded != initialized != effect-owned
```

Source-backed details:
- Microsoft loader documentation separates full-path loads from module-name search and documents several search-order modifiers: Safe DLL search mode, SxS / manifest redirection, loaded-module list, KnownDLLs, package dependency graph, application directory, current directory, PATH, and loader APIs / flags.
- Microsoft also notes that dependencies can be searched by module name even when the top-level DLL was loaded by full path, making dependency hijacks a distinct proof object.
- MSRC’s DLL planting triage frames the searched directory class — application directory, current working directory, PATH — as part of the exploitability and proof question.
- Mandiant’s side-loading / hijacking discussion grounds the host-to-DLL contract: identify the legitimate host, dependency or `LoadLibrary` request, required exports, module-load result, and payload behavior.
- Red Canary’s detection guidance reinforces practical observation surfaces: host process execution path plus DLL load monitoring are stronger than directory inventory alone.

## Reflections / synthesis

This was a good malware-branch extension because DLL search-order hijacking is common in malware triage, but the analyst error is usually not naming the ATT&CK technique. The error is treating a signed host, nearby DLL, sandbox label, or image-load event as if it already proves the later payload consequence.

The new workflow page should prevent three overreads:
1. **co-location overread** — suspicious DLL beside a host does not prove the host requested it
2. **loader overread** — one host launch does not prove this path won KnownDLL / SxS / SafeDllSearchMode / loader-flag resolution
3. **effect overread** — module-load truth does not prove initialization, export compatibility, proxy-forwarding, payload handoff, or later effect ownership

This also gives the malware branch a clean bridge to native loader/provider notes: once the malicious module is already loaded and initialized, downstream proof can route into packed-loader, native plugin-loader, runtime evidence, or first-request workflows instead of bloating the search-order page.

## Concrete scenario notes or actionable tactics added this run

Added a concrete workflow with these tactics:
- freeze one host process instance, including path, signer/hash, parent, current directory, and trigger route
- prove the unresolved DLL request through imports, delay-loads, explicit `LoadLibrary*`, dependency resolution, or loader telemetry
- freeze search posture before claiming the winning path: SafeDllSearchMode, SxS, KnownDLLs, loaded-module list, loader APIs/flags, current directory, application directory, system directories, and PATH
- prove the suspicious path won with image-load telemetry, ETW/debugger evidence, process module list, or remove/rename compare
- check exports, `DllMain`, TLS callbacks, proxy-forwarding, and host survival before claiming behavior ownership
- tie one downstream payload, persistence, comms, child-process, file/registry/network/IPC effect to the loaded module or its next stage
