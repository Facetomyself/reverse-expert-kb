## New findings
Primary durable split reinforced this run:

```text
callback slot listed
  != callback slot replayed in this run
  != replay reason matches DLL_PROCESS_ATTACH
  != startup-owned callback work
  != first payload-bearing consumer truth
```

A second practical split reinforced this run:

```text
TLS callback hit before OEP
  != same callback owns the startup path that matters
  != callback body already owns payload behavior
```

Concrete durable reinforcements preserved in the KB:
- Microsoft’s PE format documentation now gives exact TLS callback `Reason` values, so startup (`DLL_PROCESS_ATTACH`) can stay separate from thread-lifecycle (`DLL_THREAD_ATTACH` / `DLL_THREAD_DETACH`) and process-teardown (`DLL_PROCESS_DETACH`) truth
- the PE spec also preserves that callback arrays are ordered and null-terminated, so multi-callback samples should not be flattened into one generic “TLS callback exists” proof object
- the same PE documentation preserves a useful load-path caveat for static TLS in dynamically loaded DLLs, which is enough to keep OS/load-path realism visible in edge cases rather than treating on-disk TLS presence as universal replay truth
- Microsoft’s DllMain and DLL best-practice pages keep loader-context startup work honest enough to preserve a conservative reminder that early callback-visible work can still be runtime/bootstrap setup rather than payload ownership
- practitioner material sharpens both sides of the seam: Hex-Rays / Ring Zero reinforce early pre-entry execution and debugger surprise, while the recent Rust-sample writeup shows a callback can still be legitimate runtime initialization rather than the first payload-bearing consumer
