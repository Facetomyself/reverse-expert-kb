## New findings
Primary durable split reinforced this run:

```text
submitted / queued
  != retired or safely reusable
  != usbmon completion visible
  != callback finished
  != first completion consumer proved
  != later visible consequence truth
```

A second cancel-heavy split reinforced this run:

```text

  != callback cannot still run
  != object is safe to free or reuse
  != parser/router will never still see bytes or status
```

A third capture-heavy split reinforced this run:

```text
usbmon status/actual_length visible
  != full payload captured
  != full parser input truth
  != first behavior-owning consumer truth
```

Concrete practical reinforcements preserved in the KB:
- Linux kernel URB documentation preserves that `usb_submit_urb()` is asynchronous, `usb_unlink_urb()` normally returns before completion handler finish, and `usb_kill_urb()` waits until the URB is returned and the completion handler has finished; that is strong source-backed support for separating queueing truth, cancel request truth, and safe-idle truth
- the same kernel documentation preserves that even when unlink or error is reported, some data may already have transferred because USB transfers are packetized; that is a practical reminder that status/cancel truth is weaker than “no bytes ever mattered”
- the same kernel documentation explicitly warns never to sleep in a completion handler because callbacks are often called in atomic context; that keeps callback visibility separate from broad downstream parser/business logic ownership
- the same kernel documentation preserves that interrupt URBs are not automatically restarted and must be resubmitted by the completion handler if the analyst expects continuous polling; that prevents repeated traffic from being overread as one static owner without freezing resubmit truth
- usbmon documentation preserves that traces are driver-to-HCD requests rather than perfect bus truth, that callback (`C`) events report actual length, that data may be absent even when length is nonzero, and that the binary API separates `length`, `len_cap`, and dropped-event counters; that gives a conservative, source-backed reason to keep monitor-visible completion metadata separate from full parser-input truth
- accessible libusb documentation surfaces preserve that async submission and completion are separate, that `libusb_cancel_transfer()` is asynchronous/non-blocking and later callback delivery carries `LIBUSB_TRANSFER_CANCELLED`, that `status` and `actual_length` are callback-time truth, and that isochronous transfer `COMPLETED` can still hide per-packet errors; that grounds the same separation on the user-space side
