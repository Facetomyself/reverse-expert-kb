## New findings

Primary durable split reinforced this run:

```text
service file / activatable name found
  != bus instance and policy path selected
  != current owner / unique connection identified
  != activation request succeeded
  != name acquired by the process that matters
  != object path / interface / member contract selected
  != method call delivered to that owner
  != binding dispatch reached the native handler
  != first handler-owned consumer / side effect
```

Source-backed details:
- The D-Bus tutorial and specification separate bus names, unique connection names, object paths, interfaces, members, method calls, and replies. That gives the workflow its contract-selection ladder.
- The D-Bus specification describes activation / auto-start as a bus-mediated launch path: if a well-known name has no owner but is activatable, the bus can start the service, wait for it to request the name, then deliver the held message.
- `.service` files map well-known names to executables, but system-bus service files require `User=` and service-file search-path priority can decide which definition wins.
- `SystemdService=` can delegate activation to systemd, so D-Bus service metadata, systemd unit identity, and eventual process identity remain separate proof objects.
- The same specification notes policy / AppArmor mediation around auto-start and delivery, so “activatable” is weaker than “call delivered.”
- `busctl(1)` provides practical proof surfaces: `list --activatable`, `status`, `monitor`, `capture`, `tree`, `introspect`, and `call`, plus `--auto-start=` and `--expect-reply=` knobs that matter for interpreting delivery and reply/error truth.

## Reflections / synthesis

This was a good native-branch extension because D-Bus is a common Linux service ingress surface but was nearly absent from the KB except as an anti-instrumentation clue.

The new page should prevent three practical overreads:
1. treating `.service` / `SystemdService=` launch metadata as if it proves current execution
2. treating introspection XML as if it proves handler execution
3. treating a method call result as if it proves the first behavior-owning consumer without tying it to current unique owner, binding dispatch, and handler-side effect

The compact branch memory is:

```text
listed != activatable != owned != delivered != dispatched != consumed
```

That gives Linux D-Bus service work the same proof-object discipline already used in Windows service, GUI, protocol, and malware persistence branches.

## Concrete scenario notes or actionable tactics added this run

Added a concrete workflow with these tactics:
- choose system vs session/user vs container/custom bus before trusting name visibility
- record acquired vs activatable state and current unique owner / PID at call time
- treat `.service`, `Exec=`, `User=`, `SystemdService=`, and systemd aliases as activation hypotheses, not handler proof
- use introspection / object tree only to select one object/interface/member/signature
- prove method delivery with bus-level monitoring/capture and reply/error/timeout interpretation
- cross the binding dispatch boundary into GLib/GDBus, QtDBus, sd-bus, libdbus, or custom message dispatch
- push one hop past handler entry to a state write, policy reducer, worker enqueue, file/network/IPC effect, reply branch, or signal/property-change consumer
