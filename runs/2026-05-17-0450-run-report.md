## New findings
- Linux Netlink is a recurring control/event-plane surface where capture visibility is easy to overread: family discovery, Generic Netlink command selection, ACK, dump completion, multicast delivery, and local callback/parser consumption are distinct proof objects.
- Generic Netlink specifically uses `nlmsg_type` as the family ID and `genlmsghdr.cmd` as the family operation, so a reverser can mis-route dispatch analysis if they treat family ID as operation truth.
- `NLM_F_ACK` / `NLMSG_ERROR(error == 0)` is request acceptance truth, not downstream state/effect ownership.
- Multipart dumps require `NLMSG_DONE` and consistency/loss posture before object absence is meaningful.
- `nlmsg_pid` is a Netlink port ID rather than guaranteed process identity; multiple sockets in one process and sequence-0 async notifications can break naive PID/sequence matching.
- Kernel-to-user delivery can lose events, so absence of notification needs receive-loss / resync handling before it becomes evidence of no state change.

## Reflections / synthesis
The protocol/firmware branch is now broad, but Netlink was still a practical gap because it sits between protocol recovery, native Linux service analysis, firmware Linux userland, and kernel-adjacent malware. The new page adds operator value by preventing a common flattening error:

```text
Netlink traffic visible == state transition proved
```

The better proof ladder is:

```text
family/control discovered
  != operation/command selected
  != request accepted / ACKed
  != dump completed consistently
  != notification delivered to this socket
  != local callback/parser consumed it
  != state/effect owned by that consumer
```

This keeps the branch practical without returning to dense browser/mobile surfaces or doing index-only maintenance.
