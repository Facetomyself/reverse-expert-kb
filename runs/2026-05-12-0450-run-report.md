## Reflections / synthesis

The malware branch already had strong Windows persistence/hijack leaves and several Linux persistence leaves, including a new LD_PRELOAD / dynamic-linker consumer-proof note from the prior run. PAM is adjacent to that Linux userland-hijack branch, but it has a different proof shape: the decisive evidence is often not loader acceptance, but service stack selection, include/substack expansion, control semantics, PAM API entry, and one authentication/session/credential consequence.

Official Linux-PAM material makes the split practical:
- `/etc/pam.d/<service>` and `/etc/pam.conf` differ in service naming and precedence; machine-local and vendor defaults can diverge
- `auth`, `account`, `password`, and `session` are different management groups, and `pam_exec` exposes `PAM_TYPE` values such as `auth`, `open_session`, and `close_session`
- control syntax (`required`, `requisite`, `sufficient`, `optional`, `include`, `substack`, and bracketed actions) can make a visible line weaker or stronger than it first appears
- `pam_exec` can be visible but not fire due to `type=` mismatch or stack semantics, and a fired command still needs environment / UID / downstream effect proof
- reported malware cases include replaced modules, PAM API usage, credential logging, magic-password-style access, and LD_PRELOAD-adjacent PAM API hooks, so the first discriminant is which consumer family actually owns the current effect

The resulting KB delta is not “PAM can be abused.” It is a reverse-analysis stop rule: prove one target service attempt selected the relevant stack, reached the module or command, and produced the bounded effect before writing a durable behavior claim.

## Concrete scenario notes or actionable tactics added this run

Added a new workflow note with concrete tactics:
- freeze the exact service name (`sshd`, `sudo`, `login`, GDM, or another PAM-aware application) before treating a PAM line as behavior-owned
- expand include/substack paths such as `common-auth`, `system-auth`, or `password-auth` before assigning ownership to one line
- preserve control semantics separately from line visibility, especially for `sufficient`, `optional`, bracketed actions, `include`, and `substack`
- distinguish module replacement / custom module entry from `pam_exec` child-command execution and LD_PRELOAD/API-hook-adjacent cases
- for `pam_exec`, preserve `PAM_SERVICE`, `PAM_TYPE`, `PAM_USER`, `PAM_RHOST`, real/effective UID posture, and `expose_authtok` posture before claiming command-owned credential/session behavior
- stop only when one bounded authentication/session/credential effect belongs to the module entry or command-fired event
