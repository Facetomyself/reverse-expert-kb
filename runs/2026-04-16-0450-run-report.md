## New findings
Primary durable split reinforced this run:

```text
query or key ref visible
  != access-control policy on the item/key known
  != reusable auth context already satisfied
  != prompt shown for the decisive reason
  != private-key signing operation attempted
  != signature bytes returned
  != request field consumed
  != same-request signing consequence
```

A Secure Enclave-specific split reinforced this run:

```text
Secure Enclave key ref retrieved
  != raw private key recovered
  != current sign operation succeeded
  != request-owned signature proved
```

Concrete practical reinforcements preserved in the KB:
- Apple documents `kSecUseAuthenticationContext` as an `LAContext` whose prior authentication state can satisfy later keychain operations without another prompt; that is strong evidence that prompt absence is weaker than no-auth truth
- Apple documents `kSecUseOperationPrompt` as prompt-string configuration; that makes prompt wording/presence UI truth first, not automatic key-use truth
- Apple’s Face ID / Touch ID keychain sample explicitly combines `SecAccessControlCreateWithFlags(...)`, `kSecAttrAccessControl`, and `kSecUseAuthenticationContext`, and shows `touchIDAuthenticationAllowableReuseDuration`; that gives a concrete source-backed reason to separate recent-unlock reuse, fresh prompt truth, and later sign-operation truth
- Apple documents `SecAccessControlCreateFlags.privateKeyUsage` as a real usability gate for Secure Enclave signing keys; attempts to use it outside Secure Enclave generation fail, and signing with a Secure Enclave private key generated without it fails
- Apple documents `SecKeyCreateSignature(...)` as the actual private-key operation boundary that returns signature data or failure
- Apple’s Secure Enclave article explicitly says the app never handles the plain-text private key and only receives operation outputs; that supports the operator rule that a `SecKeyRef` or retrieved key handle is capability truth before it is signature-consumer truth
- Apple’s `SecItemCopyMatching` docs explicitly warn that `kSecReturnData` and `kSecMatchLimitAll` cannot be combined for password items because copying each password item could require additional authentication; that reinforces the broader practical rule that returned shape and authentication behavior are coupled strongly enough to distort naïve bulk-dump reasoning
