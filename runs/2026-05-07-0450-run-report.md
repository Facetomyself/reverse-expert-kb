## New findings

Primary durable split reinforced this run:

```text
mapping / allocation selected
  != bytes written or decoded into that exact range
  != executable protection and cache/coherency readiness proved
  != control transferred into that range
  != bytes decoded as stable code at the executed snapshot
  != first ordinary consumer or behavior-bearing effect proved
```

Compact branch memory:

```text
mapped != written != executable/coherent != transferred != decoded != consumed/effected
```

Source-backed details:
- Microsoft `VirtualProtect` documents protection changes over committed pages and explicitly ties executable generated code to caller-side cache coherency responsibility.
- Microsoft `FlushInstructionCache` documents instruction-cache flushing for generated or modified code because the CPU may otherwise execute old cached instructions.
- Linux `mmap(2)` and `mprotect(2)` separate mapping creation from page-protection transitions, with architecture caveats around `PROT_EXEC`, `PROT_READ`, and `PROT_WRITE` implications.
- Self-modifying-code unpacker literature frames modification/unpacking phases and later transfer into unpacked code as distinct phase boundaries; some early self-modification can be obfuscation-only before the main unpacker or payload.
- Practitioner unpacking workflows use executable allocation/protection and execute breakpoints as useful reduction surfaces, but those surfaces still need downstream consumer proof before naming final payload behavior.

## Reflections / synthesis

This was useful because the KB already had broader packed-stub/OEP guidance and artifact-to-consumer guidance, but dynamic executable-memory proof has its own failure mode. Analysts can observe a region become executable, break on first execution, dump bytes, and still be one stage too early. The range may be another unpacker phase, a trampoline, a thunk slab, a VM helper, a JIT cache, a wrong generation, or a pre-fixup snapshot.

The new workflow note should prevent six overreads:
1. **allocation overread** — a fresh or RWX region is not automatically payload
2. **write overread** — bytes may be transient, partial, encrypted, overwritten, or generation-specific
3. **protection overread** — executable permission is readiness evidence, not first execution
4. **cache/coherency overread** — generated-code readiness and visible instruction-cache flushing are separate from consumer proof
5. **transfer overread** — a jump/call/return into the range may enter another loader stage or trampoline
6. **disassembly overread** — code-shaped bytes are not final until one downstream ordinary consumer/effect is tied to the executed snapshot

This keeps the deobfuscation branch practical and case-driven: the operator gets a breakpoint/dump/evidence package plan rather than another abstract statement that self-modifying code is hard.

## Concrete scenario notes or actionable tactics added this run

Added a concrete workflow with these tactics:
- select one candidate dynamic-code range with base, size, page-rounded coverage, provenance, owner, and late behavior sought
- prove byte production into that exact range, including generation reuse and final-write window
- freeze executable/cache readiness separately from first execution
- catch first transfer into the range and record source site, target, generation, register/stack state, and whether the target is payload, trampoline, thunk, dispatcher, or another stub
- snapshot the executed generation at the right moment rather than dumping stale allocation/protection state
- require one ordinary consumer/effect such as parser/config use, request-builder use, policy state mutation, child/thread/callback launch, network/file/registry/device effect, or static reopen with stable xrefs before naming final payload ownership
