## New findings
Primary durable split reinforced this run:

```text
interface described
  != server registered
  != transport/endpoint listening
  != endpoint published
  != client binding object constructed or endpoint resolved
  != live client reachability on the path that matters
  != meaningful method dispatch or later consequence
```

A smaller Windows-RPC-specific split reinforced this run:

```text
MIDL/generated IfSpec or recovered interface UUID
  != RpcServerRegisterIf* runtime registration
  != RpcServerUseProtseq* / RpcServerInqBindings receive-side binding truth
  != RpcEpRegister endpoint-map publication
  != RpcStringBindingCompose / RpcBindingFromStringBinding binding-object truth
  != same server/path currently reachable for the client that matters
```

Concrete practical reinforcements preserved in the KB:
- Microsoft’s interface-registration documentation preserves that `RpcServerRegisterIf`, `RpcServerRegisterIfEx`, and `RpcServerRegisterIf2` populate the internal interface registry table used to map interface/object UUIDs to manager EPVs; static interface material is therefore weaker than runtime registration
- `RpcServerRegisterIfEx` documentation also preserves that registration can carry auto-listen and per-interface security callback behavior, which is a practical reminder that registration truth alone is still not whole-call comparability truth
- `RpcServerUseProtseqEp` and `RpcServerInqBindings` documentation preserves that receive-side bindings are their own proof object, and that successful protocol-sequence registration does not guarantee every interface/path/network interface the analyst may be imagining
- `RpcEpRegister` documentation preserves that endpoint-mapper publication is a separate step that adds or replaces server-address information in the local endpoint-map database, with explicit interface/binding/object/annotation content
- `RpcMgmtInqIfIds` documentation preserves that interface inquiry is stronger than a static roster but still requires the server to be listening
- `RpcMgmtEpEltInqBegin` preserves that endpoint-map inquiry is publication/discovery truth, with explicit match modes by interface/object UUID, rather than automatic same-client call success truth
- `RpcBindingFromStringBinding` preserves a crucial operator warning: creating a binding handle from a string binding does **not** contact the server, and success/failure does **not** indicate server availability
- `Finding Endpoints` preserves that partially bound handles are preferred for dynamic endpoints and that endpoint-map searches are still a separate discovery step, which keeps binding-object construction distinct from live reachability

## Concrete scenario notes or actionable tactics added this run
- if you only have a static UUID, `IfSpec`, or RpcView-style roster, keep working until you freeze whether `RpcServerRegisterIf*` actually ran in the runtime/configuration that matters
- if `RpcServerRegisterIf*` is visible, ask whether `RpcServerUseProtseq*` / `RpcServerInqBindings` has proved the receive-side bindings you actually care about
- if an endpoint-mapper entry exists, treat it as publication/discovery truth first, not automatic same-client reachability truth
- if a replay harness can build a binding handle with `RpcStringBindingCompose` / `RpcBindingFromStringBinding`, do **not** confuse that with proof that the server was contacted or available
- preserve one narrow chain: description -> registration -> listening/bindings -> publication -> binding object -> reachability -> dispatch/consequence
- if those earlier rungs are already solved and compare/replay still lies, hand off to the narrower Windows RPC auth-info/context-lineage note instead of reopening basic service-contract realism
