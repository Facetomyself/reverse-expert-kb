## New findings

Primary durable split reinforced this run:

```text
pipe name / instance visible
  != current client connection accepted
  != correct request bytes read on this pipe instance
  != client identity / token / impersonation level frozen
  != ImpersonateNamedPipeClient succeeded for the last read message
  != operation executed while impersonation lifetime was active

```

Compact branch memory:

```text
pipe != connected != read != impersonated != in-lifetime operation != consumed/effected
```

Source-backed details:
- Microsoft documents `ImpersonateNamedPipeClient` as changing the calling thread to impersonate the security context of the **last message read from the pipe**, and warns that failures must be checked because otherwise later work remains in the server process security context.
- Microsoft's concept page makes impersonation level part of the proof object; clients can control the server's impersonation level via `SECURITY_SQOS_PRESENT` when opening the client end.
- Microsoft named-pipe security documentation makes DACL/default-security/access-check behavior part of endpoint proof, not decoration.
- Microsoft overlapped-I/O pipe-server examples show why connect/read/write completion and per-instance state must be separated from handler truth.
- Project Zero's named-pipe client-PID spoofing research is a practical warning that `GetNamedPipeClientProcessId` is weak as standalone trust proof; PID evidence should reduce candidates, not replace token/SID/session/request proof.

## Reflections / synthesis

This was a useful native-branch addition because named-pipe analysis has a distinctive false certainty pattern. Analysts often find a pipe name, observe a client PID, or see `ImpersonateNamedPipeClient(...)` and then narrate the later handler as if the identity and operation boundary are settled. In reality, the proof may depend on which pipe instance was reused, which request was the last read message, whether overlapped completion selected the right state, whether impersonation succeeded, what impersonation level was effective, and whether the behavior-bearing operation happened before `RevertToSelf` or on a different worker thread.

The new workflow page should prevent six overreads:
1. **endpoint overread** — pipe name / `CreateNamedPipe*` visibility does not prove the current accepted client/request
2. **request overread** — connection success does not prove the last read message owns the next impersonation
3. **identity overread** — PID/image hints are not durable token/SID/impersonation-level proof
4. **impersonation overread** — a static callsite does not prove return success or thread-token lifetime
5. **lifetime overread** — token capture or impersonation may not cover later queued/worker operations
6. **handler overread** — a dispatch branch is not final until one in-lifetime operation or downstream effect is tied to the request

This gives the native branch a clean Windows service/IPC counterpart to the Linux D-Bus and Unix-domain socket seams while also connecting to malware service-abuse and runtime-evidence packaging pages.

## Concrete scenario notes or actionable tactics added this run

Added a concrete workflow with these tactics:
- freeze pipe name, mode, security descriptor/default DACL, remote-client posture, and concrete instance before narrating trust boundary
- tie `ConnectNamedPipe`, `ReadFile` / `GetOverlappedResult`, request bytes, and per-instance state to one client request
- treat PID/image/session evidence as a reduction clue, then cross-check token/SID/impersonation level when identity matters
- break on `ImpersonateNamedPipeClient`, record return value, thread ID, current thread token, and `RevertToSelf` timing
- require one resource operation, state mutation, process launch, reply, or downstream effect while the relevant impersonation lifetime is active before claiming handler ownership
