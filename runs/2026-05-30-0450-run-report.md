## New findings
- `io_uring(7)` separates ring setup, SQE preparation, `io_uring_enter(...)`/submit notification, CQE visibility, and application CQE processing. Prep helpers are request-construction evidence, not accepted kernel work or app-side effect proof.
- Completion order is not submission order. The manual explicitly warns that requests can complete in any order; request identity should be recovered through `user_data` or equivalent target-local ownership, not SQE slot reuse or nearby buffer addresses.
- `io_uring_sqe_set_data(3)` warns that if `user_data` is not assigned, the SQE field can retain a previous value. Stale `user_data` is therefore a possible false-owner source in reverse cases.
- `io_uring_cqe_seen(3)` marks a CQE as consumed and allows slot reuse. CQE presence in the shared ring is completion-availability truth, not proof that the target dispatcher, parser, state reducer, or lifetime transition consumed it.
- Cancellation is racy and two-sided: a cancel request has its own CQE, while the original request may complete, cancel, or race into `-EALREADY` / `-ENOENT` interpretations. The cancel CQE and original request CQE must be reconciled before claiming safe owner retirement.
- Multishot operations invert the ordinary one-SQE/one-CQE assumption. `IORING_CQE_F_MORE`, final CQE semantics, buffer IDs, and per-CQE `res` must be preserved as separate lifetime and consumer evidence.
- The compact seam added this run is: **ring setup != SQE prepared != submitted/accepted != completion visible != CQE consumed/routed != request-owned effect**.

## Reflections / synthesis
This run deliberately did not continue firmware/protocol or malware handoff. Native desktop/server is now materially established, but it still has underfed Linux async primitives that are common in real server targets and easy to misread statically.

The false inference guarded against is:

```text
io_uring ring visible + SQE prep or CQE in memory == request-owned behavior proved
```

The sharper workflow is:

```text
ring instance frozen
  -> SQE prepared with opcode/fd/buffer/user_data
  -> submit boundary crossed and accepted/in-flight state considered
  -> CQE visible with res/flags/user_data/buffer-id
  -> CQE marked seen or otherwise routed
  -> target dispatcher/object/state consumer runs
  -> later effect or safe lifetime transition proved
```

The important practical distinction is that `io_uring` makes async evidence look deceptively local because the rings are ordinary shared memory. For reverse work, the rings should be treated like a small user/kernel protocol with explicit identity, ordering, cancellation, multishot, and consumer proof boundaries.
