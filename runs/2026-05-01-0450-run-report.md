## New findings

Primary durable split reinforced this run:

```text
CAN IDs found
  != ISO-TP stream reassembled
  != UDS service/subfunction/DID/RID contract selected
  != diagnostic session/security/keepalive posture valid now
  != request accepted under current preconditions
  != positive/negative/delayed response interpreted correctly
  != ECU state, routine, actuator, DTC, configuration, or flash/update consumer changed
```

Compact branch memory:

```text
ids != reassembled != service-contract != session/security-live != accepted/responded != state-consumed
```

Source-backed details:
- UDS / ISO-14229 is an application protocol interface for vehicle diagnostics, debugging, configuration, and ECU interaction; in common CAN cases it rides above ISO-TP / DoCAN rather than being identical to raw CAN frames.
- UDS uses SID-first diagnostic messages. Positive responses commonly use the request SID plus `0x40`; negative responses use `0x7F` and carry the original service plus a negative response code.
- `0x78` response-pending, positive-response suppression, timeouts, gateway behavior, and functional addressing all prevent no-response or delayed-response cases from being interpreted naively.
- Diagnostic sessions and security levels gate service availability, but a session switch or SecurityAccess success is not itself proof that a protected service reached its behavior-bearing consumer.
- DID/RID/service enumeration is a contract selector before it is state proof; the analyst still needs one handler, state write, routine worker, DTC/config update, programming transition, actuator/test effect, or follow-on ECU behavior.

## Reflections / synthesis

This was a useful protocol-branch addition because CAN / UDS work has a distinctive false certainty pattern. Tools make endpoint discovery, service scans, DID dumps, seed collection, and TesterPresent loops convenient. That convenience can make a scan result feel like a behavior proof.

The new workflow page should prevent six overreads:
1. **endpoint overread** — request/response IDs do not prove ISO-TP or UDS application truth
2. **transport overread** — reassembled payloads do not prove service semantics
3. **service overread** — supported SID / DID / RID does not prove current state consequence
4. **unlock overread** — session/security posture is a live condition, not a durable effect claim
5. **response overread** — positive/negative/delayed/absent responses need timing, suppression, gateway, and NRC interpretation
6. **effect overread** — handler acceptance is not final until one ECU state/effect consumer is tied to the exchange

This gives the protocol branch a clean bridge from automotive diagnostics into existing parser-to-state, replay-precondition, output-handoff, peripheral-effect, and firmware-context pages without turning the UDS page into a general car-hacking note.

## Concrete scenario notes or actionable tactics added this run

Added a concrete workflow with these tactics:
- freeze bus/channel/gateway, physical vs functional addressing, CAN ID width, request/response IDs, and ISO-TP behavior before interpreting UDS semantics
- select one SID/subfunction/DID/RID contract and expected positive/negative response shape
- record current session, security level, seed freshness, `TesterPresent` cadence, resets/sleeps, and suppression bits at request time
- interpret `0x7F` NRCs, `0x78` response-pending, delayed positives, suppression, and timeouts conservatively
- cross into firmware/parser/dispatcher evidence when available: SID table, precondition checks, response builder, handler ownership
- require one state field, routine worker, DTC/config update, IO/actuator path, programming state transition, or follow-on ECU behavior before claiming state/effect ownership
