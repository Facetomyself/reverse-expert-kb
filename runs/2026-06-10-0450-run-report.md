## New findings
- Microsoft’s service-trigger documentation keeps configuration, condition matching, SCM action, trigger-start argument, queued trigger controls, and accepted-control posture separate. The important operator split is that `SERVICE_TRIGGER` / `sc qtriggerinfo` is eligibility/configuration truth, not live trigger firing or service-consumer proof.
- `SERVICE_TRIGGER_STARTED_ARGUMENT` in `ServiceMain argv[1]` is useful trigger-start entry truth, but it still does not prove worker-owned behavior. It should be paired with the later route/worker/effect chain.
- When a trigger event occurs while a service is already running, SCM can send `SERVICE_CONTROL_TRIGGEREVENT`; when a service is stopping, `ERROR_SHUTDOWN_IN_PROGRESS` and later `SERVICE_ACCEPT_TRIGGEREVENT` posture affect queued trigger delivery. This makes HandlerEx and current `dwControlsAccepted` runtime posture first-class proof objects.
- Microsoft’s service-control-handler documentation explicitly warns that handlers run in the control-dispatcher context and should return quickly; long work should be moved to a secondary thread. Handler entry is usually a reduction boundary, not the first behavior-owning consumer.
- The Inbits `npsvctrig.sys` reversing note adds a concrete named-pipe trigger bridge: NPFS/minifilter observation, WNF-backed trigger lists, ETW publication, SCM consumption, and service-side pipe handling are separate boundaries. Endpoint-trigger publication is not the same as service-side request consumption.
- The compact split added this run is: **configured != fired != selected != entered != accepted/routed != handed off != consumed/effected**.

## Reflections / synthesis
This run extended the native practical branch without falling back into browser/mobile density or top-level wording-only maintenance. The service-dispatcher page already preserved `StartServiceCtrlDispatcher`, `ServiceMain`, handler registration, control-handler entry, worker handoff, and first worker consumer as separate proof objects. What it under-described was the trigger-specific lie:

```text
trigger configuration or endpoint-trigger publication == the service behavior ran because of this trigger
```

The sharper source-backed ladder is narrower:

```text
trigger source -> condition fired -> SCM selected action -> ServiceMain/HandlerEx route -> accepted-control posture -> worker handoff -> first worker-owned consumer/effect
```

This is especially useful for named-pipe/RPC endpoint triggers because the lower layer can be highly convincing: a pipe name exists, a kernel/minifilter path observes a missing pipe/open/wait condition, ETW publishes, and SCM can start the service. None of those prove that the service’s own pipe/RPC handler consumed the request or that the later behavior belongs to the trigger path.
